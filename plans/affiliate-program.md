# Партнёрская программа Artmate

Дата фиксации: 2026-09-16. Ветка: `codex/affiliate-program`, от обновлённого `origin/master`.

## Цель и границы

Отдельный кабинет `affiliate.artmate.ru` для блогеров на общей системе аккаунтов Artmate.
Заявка остаётся на публичном лендинге. После общения с менеджером блогер регистрируется,
заключает договор, а администратор связывает аккаунт с заявкой и открывает доступ.
Самостоятельной регистрации в качестве партнёра и самостоятельного изменения реквизитов нет.

Прогресс выполнения и проверки: [affiliate-progress.md](./affiliate-progress.md).
Этот план отслеживается Git; каталог `docs` в репозитории игнорируется.

## Согласованные правила

- У партнёра несколько промокодов. У каждого код и необязательный приватный комментарий,
  а не обязательное название источника. Комментарий видят партнёр и администратор.
- Общий бюджет — 20%: вознаграждение партнёра от 0 до 15%, покупателю от 20 до 5%.
  Шаг 1 процентный пункт, начальное распределение 10/10. Нулевая комиссия допустима.
- Ставки и база расчёта фиксируются в заказе; последующие изменения кода не меняют заказ.
- Подтверждённая база расчёта обеих долей — стоимость всех товаров до партнёрской
  скидки, без доставки: 1 000 ₽ и 10/10 = 100 ₽ скидки + 100 ₽ вознаграждения.
  Скидки нескольких промокодов не суммируются.
- Начисления учитывают оплаты через T-Bank и Ozon Pay. Неоплаченный заказ не создаёт
  доступное вознаграждение. Оплаченное начисление сначала ожидает подтверждения.
- После завершения заказа и 14 дней подтверждения сумма становится доступной.
- Собственные покупки партнёра получают скидку, но не вознаграждение. Совпадение
  аккаунта проверяется сервером. По решению пользователя от 17 сентября выявление
  связанных аккаунтов пока отложено и не входит в текущий запуск.
- Полный возврат отменяет вознаграждение. Частичный — долю по возвращённым товарам.
  Возврат одной доставки не уменьшает комиссию. Повторные события не дублируют проводки.
- Если деньги уже выплачены, возврат создаёт задолженность, погашаемую следующими
  начислениями. Незавершённая заявка на выплату при таком возврате отменяется с причиной;
  после перерасчёта партнёр подаёт новую.
- Баланс общий по всем кодам: ожидается, доступно, зарезервировано, выплачено, задолженность.
  Источник истины — журнал операций, а не вручную изменяемое поле «баланс».
- Минимум выплаты по умолчанию — 5 000 ₽. В профиле заложено персональное переопределение
  администратором. `null` означает общий порог. Порог фиксируется в заявке на выплату.
- Партнёр указывает сумму заявки от действующего минимума до доступного остатка
  включительно; резервируется только выбранная сумма. Не больше одной открытой заявки.
  Выплата вручную администратором с фиксацией даты и подтверждения.
- Реквизиты берутся из подписанного договора. Партнёр видит их только для чтения.
  Изменения администратором версионируются; заявка на выплату хранит снимок реквизитов.
- Публично перечень партнёрских промокодов не публикуется. Данные покупателей партнёру
  не раскрываются; аналитика содержит только необходимые обезличенные сведения.

## Архитектура

Новый Yarn workspace `apps/affiliate`, Next.js 16 / React 19 / TypeScript, локальный порт 3006.
Общий NestJS backend `apps/api`, отдельный доменный модуль `affiliate`.
Управление партнёрами остаётся в `apps/admin`. Витрина не импортирует код кабинета.

Основной архитектурный образец — `apps/site`. Дополнительные примеры FSD можно читать
из `/Users/denis.voropayev/Desktop/projects/msb-*`, не перенося их инфраструктуру и зависимости.

```text
app/                 маршруты, metadata, server guards, hydration
src/_app/            провайдеры, layouts, data builders
src/_pages/          только сборка страниц
src/features/        сценарии, формы, mutations, состояния запросов
src/entities/        доменные read-модели, query options/hooks, read-only UI
src/widgets/         повторяемые крупные блоки навигации/layout
src/shared/          shadcn primitives, транспорт, инфраструктура, константы
```

Импорты только вниз через public API слайсов. `shared/actions` — только транспорт,
без toast, revalidate сценариев и UI-контрактов. Формы — React Hook Form + zod,
DTO builders и UI-state в `features/*/lib`, mutations отдельными hooks в `model`.
Страницы не читают query и не управляют бизнес-сценариями. Сервер проверяет права
независимо от скрытых кнопок. Персональные ответы не кэшируются публично.

## Визуальное направление

Использовать существующие shadcn/ui (`radix-nova`), стилизовать через брендовые tokens.
Шрифты и палитра Artmate: Nunito, Comfortaa, светлая основа, тёмный акцентный блок,
розовый, оранжевый и фиолетовый. Вдохновение — современные crypto/wallet-интерфейсы,
без криптовалютной функциональности и постороннего неонового брендинга.

Крупные понятные показатели, аккуратные карточки и интервалы, короткие подписи,
цветное распределение 20%, карточки промокодов и график дохода на соответствующих этапах.
Не показывать выдуманные продажи, доходы или неработающие активные элементы.
Пользовательские тексты — человеческие и короткие: без «Только для чтения»,
«на следующем этапе», «будущие модули» и пояснений процесса разработки.
Неготовые разделы скрывать, а не заменять техническими заглушками.
Мобильный интерфейс полноценный: нет горизонтального скролла страницы, перекрытий
навигацией, нечитабельных таблиц и обрезанных реквизитов.

## Этапы и критерии готовности

1. **Доступ и договоры.** Роль `partner`, профиль, связь с существующей заявкой,
   активный/приостановленный доступ, договор и реквизиты с историей версий,
   персональный порог. Администратор выбирает существующий аккаунт; сохранение
   полного профиля выдаёт доступ. Одно одобрение заявки доступа не даёт.
2. **Основа кабинета.** Новый workspace, вход существующим аккаунтом, серверный контроль
   доступа, фирменный адаптивный layout, реальные данные сотрудничества только для чтения.
   Блоки финансов и кодов не имитируют готовую функциональность до следующих этапов.
3. **Промокоды.** Создание нескольких кодов с необязательным комментарием, настройка
   распределения, приостановка и серверные ограничения. Привязка к существующему
   механизму промокодов; без параллельного движка скидок.
4. **Заказы и возвраты.** Снимки условий, расчёты в копейках, события обеих платёжек,
   идемпотентные начисления и сторнирования, частичные возвраты, подтверждение дохода.
5. **Баланс и аналитика.** Журнал операций, показатели и динамика, продажи по кодам,
   фильтры периодов, отсутствие персональных данных покупателей.
6. **Выплаты.** Резервирование транзакцией, персональный минимум, одна открытая заявка,
   снимок договора/реквизитов, админ-обработка и отзыв при возврате, защита от гонок.
7. **Запуск.** CI, Docker и reverse proxy, env-путь целиком, DNS/TLS с разрешением,
   полный регресс, мобильная проверка, пробный партнёр и контроль расчётов.

Первый рабочий инкремент объединяет этапы 1–2. После его проверки продолжаем с кодами.
В этом инкременте не применять миграции к удалённым БД, не менять production/DNS,
не совершать реальные выплаты. Коммиты и push — только отдельным запросом.

## Контракт первого инкремента

Все даты API — ISO 8601, деньги — целые копейки. Роль API `partner`, Prisma `PARTNER`.

`AffiliatePartnerSummary`:

```ts
{
  id: string;
  userId: string;
  userName: string | null;
  userEmail: string | null;
  status: "active" | "suspended";
  partnerApplicationId: string | null;
  minimumPayoutKopecks: number | null;
  effectiveMinimumPayoutKopecks: number;
  contractVersion: number;
  createdAt: string;
  updatedAt: string;
}
```

`AffiliatePartner` = summary + `contract: { number: string; signedAt: string; paymentDetails: string }`.
В списках реквизитов нет. `AffiliateContractRevision`:
`{ version: number; number: string; signedAt: string; paymentDetails: string; changedAt: string; changedByUserId: string }`.

| Метод | URL                                                       | Ответ / назначение                                            |
| ----- | --------------------------------------------------------- | ------------------------------------------------------------- |
| GET   | `/affiliate/me`                                           | `AffiliatePartner`; только собственный активный профиль       |
| GET   | `/affiliate/admin/partners?page=1&pageSize=25&search=...` | `{ items: AffiliatePartnerSummary[], total, page, pageSize }` |
| GET   | `/affiliate/admin/partners/:userId`                       | `AffiliatePartner`; 404 если профиля нет                      |
| PUT   | `/affiliate/admin/partners/:userId`                       | создать/изменить профиль, вернуть `AffiliatePartner`          |
| GET   | `/affiliate/admin/partners/:userId/history`               | `AffiliateContractRevision[]`, новые сверху                   |

PUT принимает `{ status, partnerApplicationId: string|null, minimumPayoutKopecks: number|null,
contract: { number, signedAt, paymentDetails } }`. Все поля обязательны, строки договора
непустые; id заявки nullable, но при наличии реальный и не связан с другим партнёром.
`minimumPayoutKopecks` — положительное safe integer либо null. Дата договора не в будущем.
Форма редактирует календарную дату: новая дата передаётся как ISO datetime с UTC-midnight,
при неизменённой дате сохраняется исходный timestamp. Дата UTC из `signedAt` сравнивается
с текущим календарным днём `Europe/Moscow`, чтобы сегодняшняя дата была допустима
с московской полуночи. В интерфейсах дата договора отображается без сдвига UTC-дня.
Профиль создаётся только существующему активному зарегистрированному аккаунту:
подтверждённая email-регистрация или существующий Yandex OAuth account. Не требуем
`emailVerifiedAt` от OAuth-пользователей: текущий Yandex flow его не заполняет.
Техническая запись гостя без регистрации и неподтверждённая email-регистрация не подходят.
Администратор выбирает его из существующего `GET /users`, а заявку — из текущего API заявок.

Активировать доступ без заполненного договора/реквизитов нельзя. Выдача роли и запись
профиля атомарны. При приостановке роль отзывается; повторная активация восстанавливает.
Изменение членства `partner` через общий редактор ролей запрещено: только через профиль,
чтобы не обходить проверку договора. Проверять текущие права на сервере, не доверять
только роли из JWT. Изменения договора сохранять в неизменяемой истории с актором,
новую версию создавать только при изменении полей договора.

Вход кабинета использует существующие `/auth/login`, `/auth/session`, `/auth/logout`
через server actions, защищённый HttpOnly cookie, имеющуюся CSRF-защиту и transport patterns.
Не добавлять отдельную базу пользователей. Междоменный вход при развёртывании требует
проверки действующей настройки `AUTH_COOKIE_DOMAIN`; не расширять её молча.

Домен подтверждён пользователем: основной `artmate.ru`, кабинет `affiliate.artmate.ru`.
Упоминания `art-mate.ru` в текущих примерах конфигурации относятся к старому домену.
Новый кабинет использует актуальный адрес. При инфраструктурном этапе проверить
env, reverse proxy, TLS и возможность общей cookie для `.artmate.ru`;
сейчас не менять production/DNS или cookie scope.

## Контракт второго инкремента: партнёрские промокоды

Этап 3, без включения выплат и без применения миграций к рабочим БД.
Переиспользуем `PromoCode` и существующий расчёт скидок, добавляем вид `affiliate`.
Код связан с партнёром, хранит `partnerPercent` и приватный `comment` отдельно от
публичного описания. Скидка покупателя = `20 - partnerPercent`, допустимо 0–15,
только целые проценты. Существующие лимиты/даты не редактируются партнёром.
Сгенерированный код: `ARTM-` + 6 символов из текущего алфавита без неоднозначных знаков.
Можно задать свой код по существующим правилам; после создания строка кода неизменна.

`AffiliateCode`: `{ id, code, comment: string|null, partnerPercent, buyerPercent,
isActive, createdAt, updatedAt }`. Даты ISO; комментарий trim, максимум 500 символов.
GET списков возвращает `{ items: AffiliateCode[], total, page, pageSize }`, новые сверху,
по умолчанию page=1/pageSize=20, максимум pageSize=100.

| Метод | URL                                               | Назначение                                                         |
| ----- | ------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------- |
| GET   | `/affiliate/codes`                                | Только собственные коды активного партнёра                         |
| POST  | `/affiliate/codes`                                | `{ code?: string, comment?: string                                 | null, partnerPercent: number }`, активный код |
| PATCH | `/affiliate/codes/:codeId`                        | `{ comment?, partnerPercent?, isActive? }`, только собственный код |
| GET   | `/affiliate/admin/partners/:userId/codes`         | Коды партнёра для администратора                                   |
| PATCH | `/affiliate/admin/partners/:userId/codes/:codeId` | Тот же update-контракт, с проверкой владельца                      |

Обычный admin promo editor не меняет партнёрские коды: API запрещает update, UI
помечает вид и направляет в партнёрский раздел. Не удаляем записи и не теряем историю.
Приостановленный партнёр не управляет кодами; его коды не принимаются в preview,
calculate и резервировании, даже если сам код отмечен активным. Учитывается актуальный
статус аккаунта/роль. Комментарий и реквизиты никогда не попадают в публичные ответы.

На резервировании в уже существующие terms snapshots заказа и redemption записываются
идентификатор партнёра, обе ставки и признак собственной покупки. Изменение ставки/пауза не меняет старые снимки.
Это фиксация атрибуции, а не финансовое начисление. Денежный ledger и правила подтверждения
следуют отдельным этапом. Пользователь подтвердил все товары до скидки без доставки,
14 дней после завершения и отсутствие вознаграждения по собственным покупкам.

Гонки create/update/reserve/suspend должны быть сериализованы согласованными row locks.
Уникальность кода глобальная; ручной дубликат — 409, автогенерация повторяет попытку
без маскировки остальных ошибок. Ограничения ставок проверяются API и SQL constraint.

UI: раздел «Промокоды», карточки, копирование, новая форма/редактирование, наглядное
распределение «Вам / Покупателю», пауза/возобновление. Комментарий необязателен, никаких
полей «источник». Только реальные действия, без заглушек будущей аналитики/выплат.
RHF+zod, shadcn, FSD, private cache/hydration, desktop/mobile QA обязательны.

## Решения до финансового этапа

- Подтверждено 16 сентября: все товары до скидки без доставки, 14 дней после завершения,
  собственные покупки со скидкой, без вознаграждения.
- Сценарий достоверной фиксации частичного возврата по позициям в обеих платёжках.
- Окончательный текст договора/условий и операционный процесс подтверждения выплат.

## Подготовка этапа 4: оплаты и ручные возвраты

Пользователь уточнил: возвраты оформляются вручную через админку. Для финансового
учёта нужен явный административный сценарий фиксации возврата: позиции/количество,
доставка, подтверждение операции, автор и дата. Дубли нельзя учитывать повторно.
Фиксация возврата и сторнирование комиссии не должны сами отправлять деньги через
платёжный API; интеграция реального банковского возврата — отдельная задача.

Текущие `orders.storage.ts` и адаптеры подтверждают оплату, но не сохраняют состав
возвращённых позиций. До сверки частичного возврата связанное начисление блокируется
для вывода; нельзя считать всю возвращённую сумму стоимостью товаров или доставки.
Фискальные price groups и оригинальная стоимость товаров уже сохранены в
`promoPricingSnapshot` — их использовать для пропорционального сторнирования.

Финансовый этап должен отдельно закрыть:

- Начисление один раз на подтверждённую оплату, только по сохранённым affiliate terms.
- Собственные покупки: проверять `checkoutActorUserId` и фактически связанный
  `order.userId`, включая гостевой checkout, связанный по email; это не полноценный
  антифрод связанных аккаунтов.
- Постоянный timestamp завершения и 14 суток до доступности; повторный callback,
  перезапуск worker и смена ставки не меняют исходные условия.
- Полный возврат, частичный возврат по позициям, доставка без сторнирования комиссии,
  возврат после доступности/выплаты и переставленные события.
- До появления подтверждённого состава частичного возврата — отдельный review-state,
  отсутствие автоматического вывода спорной суммы и явный сценарий сверки для админа.
- API обоих провайдеров нельзя расширять выдуманными refund fields: проверять
  официальную спецификацию/реальные обезличенные payloads перед автоматической сверкой.

Источники для проверки банковского контракта:
[Т-Банк: уведомления](https://developer.tbank.ru/eacq/intro/developer/notification),
[Т-Банк: возвраты](https://developer.tbank.ru/eacq/scenarios/cancel_confirm/).
В публичном поиске точная спецификация полей возвратов Ozon Pay не найдена;
маркетинговая страница банка не заменяет техническую документацию.

### Первый инкремент финансового этапа

- `Order.completedAt` фиксируется один раз при завершении из админки или CDEK.
  Оба пути блокируют и повторно читают заказ в транзакции. Доступность комиссии
  требует подтверждённой оплаты, текущего завершённого статуса и 14 полных суток.
- При подтверждённой оплате обеих платёжек атомарно создаётся единственное начисление
  с неизменяемым расчётом. Нулевая доля и собственная покупка фиксируются без дохода.
- Неизменяемый журнал начислений и сторнирований — основа будущего баланса.
  Готовых выплат/резервирования в этом инкременте нет.
- `GET /orders/admin/:orderId/refunds` возвращает остатки товаров/доставки,
  сохранённые ценовые группы, историю возвратов и начисление по заказу.
- `POST` по тому же пути принимает `requestId` (UUID), `reference`, `reason`,
  `items: [{ productId, quantity }]`, `deliveryKopecks`, `confirmed: true`.
  Количества добавочные, а не накопительные. Идентификатор запроса защищает повтор
  после сетевой ошибки, номер операции уникален в пределах заказа.
- Сумма покупателю рассчитывается по сохранённым ценам после скидки; сторнирование
  комиссии — отдельно по исходным ценам до скидки. Возврат доставки не меняет комиссию.
- В админке — «Учесть возврат», выбор количества/доставки, номер и причина операции,
  подтверждение, история с автором/датой. Сохранение не переводит деньги покупателю.
- Автоматическая сверка банковских возвратов, выплаты/задолженность и общий финансовый
  кабинет остаются следующими частями этапов 4–6. До них выплаты не включать.

## Контракт этапа 5: баланс и аналитика

- Read-only API: `GET /affiliate/analytics?days=30&codePage=1&codePageSize=10`
  и `GET /affiliate/ledger?days=30&page=1&pageSize=20`; административные аналоги
  `/affiliate/admin/partners/:userId/analytics` и `/ledger`. Собственный кабинет
  требует активной роли и профиля; администратор может читать приостановленный профиль.
- Периоды 7/30/90 дней включают сегодняшний день, границы — по Москве. От начала
  первого дня до единого `asOf`; дневные значения заполняются нулями. Пагинация
  кодов и журнала на сервере, размеры страниц до 50, агрегация в БД.
- Баланс за всё время не зависит от периода: `availableKopecks`, `pendingKopecks`,
  `heldKopecks`, `reversedKopecks`. Первые три — остаток проводок по начислению,
  распределённый по текущим оплате/статусу/сроку заказа. Последнее — суммарное сторно.
  Выплачено, резерв и задолженность до реализации выплат не имитируются нулями.
- Метрики `orderCount`, `salesKopecks`, `earnedKopecks`, `reversedKopecks`, `netKopecks`
  считаются по событиям журнала за период. Продажи — исходная стоимость товаров
  оплаченных заказов до скидки и без доставки; собственные покупки и ставка 0%
  входят в продажи, но не в доход. Возвраты не уменьшают исходное число покупок.
  Возврат старой покупки учитывается в день возврата: доход периода может быть отрицательным.
- Ответ аналитики: `asOf`, `period { days, from, to, timeZone }`, `balance`, `totals`,
  `daily` (метрики + `date` YYYY-MM-DD), `codes { items, total, page, pageSize }`.
  Код берётся из неизменяемого снимка; список включает коды с событиями периода,
  в том числе приостановленные, сортировка по коду. Текущие ставки ничего не пересчитывают.
- Журнал: `asOf`, `period`, `items`, `total`, `page`, `pageSize`. Операция содержит
  `id`, `code`, `kind` (`credit`/`reversal`), signed `amountKopecks`, `createdAt`,
  `availableAt`, текущий `status`, `isSelfPurchase`, `partnerPercent`.
  Имена/контакты покупателей, причины и банковские номера возвратов не передаются.
- Один согласованный read-only snapshot на ответ, целые копейки с контролем overflow.
  Финансовые query обновляются через 30 секунд при повторном чтении/focus и кнопкой;
  ключи изолированы по партнёру и периоду, ошибки не подменяются нулями.
- В кабинете — брендовая карточка баланса, показатели, динамика, коды и операции.
  В админке — независимый финансовый блок в профиле партнёра, вне формы договора.
  Выплаты, банковские операции, production и применение миграций в этот этап не входят.

## Уточнения интерфейса — 17 сентября 2026

- На партнёра можно создать не более 3 кодов, включая выключенные. Прежние коды
  сверх лимита не удаляются и доступны для редактирования. Лимит проверяется сервером
  в транзакции под блокировкой пользователя, в списке кодов передаётся `limit`.
  Превышение возвращает HTTP 409 и `code: "affiliate_code_limit"`; общий транспорт
  передаёт код ошибки без разбора текста, пользовательское сообщение выбирает feature.
- `held` отображается как «Приостановлено» с причиной, `pending` — «Ожидает
  подтверждения». В журнал добавляется nullable `holdReason`: `order_cancelled`,
  `payment_not_confirmed`, `order_not_completed`. Для иных статусов и сторно — `null`.
  Порядок приоритетов причин: отмена, неподтверждённая оплата, незавершённый заказ.
- Таблица дневных значений начинается с актуальной даты; график сохраняет хронологию.
  Визуализация долей не должна содержать неподвижного контрастного деления 50/50.
- Для просмотра графика используются вымышленные данные из локального mock API
  за 90 дней: переменные начисления, возвраты и дни без операций. Рабочая БД не меняется.
