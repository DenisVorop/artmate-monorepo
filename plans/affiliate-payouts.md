# Выплаты партнёрам — этап 6

Согласованное продолжение [партнёрской программы](./affiliate-program.md).
База реализации: `e02bb27`, ветка `codex/affiliate-program`. Состояние задач —
только в [affiliate-progress.md](./affiliate-progress.md).

## Сценарий

- Активный партнёр сам указывает сумму одной заявки: не меньше действующего
  минимального порога и не больше доступного остатка. В резерв уходит только
  запрошенная сумма. Реквизиты он не вводит. Минимум 500 000 копеек по умолчанию, персональное переопределение
  берётся из профиля. Снимок суммы, порога и версии договора сохраняется атомарно.
- Статусы: `pending` — «На рассмотрении», `paid` — «Выплачено», `rejected` —
  «Отклонено», `cancelled` — «Отменено». Дополнительного шага согласования нет.
- Администратор вручную переводит деньги вне системы и затем учитывает выплату
  с датой, номером операции и явным подтверждением. Сохранение НЕ вызывает банк.
  Отказ требует причины. Терминальные заявки не редактируются.
- Возврат с положительным сторнированием вознаграждения отменяет открытую заявку
  партнёра с причиной, освобождая резерв в той же транзакции. Возврат доставки
  или возврат без изменения вознаграждения заявку не отменяет.
- Возврат после выплаты создаёт дефицит доступных средств; последующие подтверждённые
  начисления сначала покрывают его. Пока есть долг, новая выплата невозможна.
- Учёт ведётся в целых копейках по неизменяемым финансовым событиям, а не редактируемому
  полю баланса. Показатели продаж и дохода не уменьшаются на сумму выплаты.
- Партнёр читает только собственные заявки. Администратор видит заявки выбранного
  партнёра, включая приостановленного, но не подтверждает выплату при отозванном доступе.
  Отклонить открытую заявку приостановленного партнёра можно.

## API-контракт

Даты ISO 8601 UTC, деньги — safe integer в копейках. Private/no-store, серверные
проверки роли, текущего статуса аккаунта/профиля и принадлежности заявки обязательны.

```ts
type PayoutStatus = "pending" | "paid" | "rejected" | "cancelled";
type PayoutEvent = {
  id: string;
  status: PayoutStatus;
  createdAt: string;
  actorUserId: string | null; // null для автоматической отмены
  reason: string | null;
};
type Payout = {
  id: string;
  status: PayoutStatus;
  amountKopecks: number;
  minimumPayoutKopecks: number;
  createdAt: string;
  updatedAt: string;
  paidAt: string | null;
  reference: string | null;
  reason: string | null;
  contract: {
    version: number;
    number: string;
    signedAt: string;
    paymentDetails: string;
  };
  events: PayoutEvent[]; // старые -> новые; без контактов покупателей
};
type PayoutSummary = {
  asOf: string;
  availableKopecks: number; // после вычета выплат и открытого резерва
  reservedKopecks: number;
  paidKopecks: number;
  debtKopecks: number;
  minimumPayoutKopecks: number; // текущий эффективный минимум
  canRequest: boolean;
  blockedReason:
    | "partner_inactive"
    | "open_request"
    | "debt"
    | "no_available_balance"
    | "below_minimum"
    | null;
};
type PayoutList = {
  summary: PayoutSummary;
  items: Payout[];
  total: number;
  page: number;
  pageSize: number;
};
```

| Метод | URL | Назначение |
| --- | --- | --- |
| GET | `/affiliate/payouts?page=1&pageSize=10` | Собственные заявки и актуальная сводка |
| POST | `/affiliate/payouts` | `{ requestId: UUID, amountKopecks: number }` -> `Payout` |
| GET | `/affiliate/admin/partners/:userId/payouts?page=1&pageSize=10` | Заявки и сводка партнёра |
| POST | `/affiliate/admin/partners/:userId/payouts/:payoutId/paid` | `{ requestId: UUID, paidAt: ISO, reference: string, confirmed: true }` -> `Payout` |
| POST | `/affiliate/admin/partners/:userId/payouts/:payoutId/reject` | `{ requestId: UUID, reason: string }` -> `Payout` |

Списки — новые сверху (`createdAt DESC`, затем `id DESC`), page >=1, pageSize 1..50.
Доступный остаток и действующий минимум вычисляются сервером при создании;
`amountKopecks` — положительное целое safe integer, от минимума до доступного
остатка включительно. Клиент не может подменить остаток или порог. Запрошенная
сумма входит в fingerprint и сохраняется в снимке, обеспеченность перепроверяется
при подтверждении. Частичная заявка не резервирует незапрошенный остаток.
Дата выплаты не в будущем и не раньше заявки. Reference trim, 1..160 символов;
reason trim, 1..1000. Подтверждение выплаты без `confirmed: true` запрещено.

Идемпотентный UUID сохраняется вместе с fingerprint операции. Повтор с тем же
содержимым возвращает исходный результат, другой payload с тем же ключом — 409.
Повтор старого create не создаёт новую заявку после завершения первой. Повтор
подтверждения выплаты не создаёт вторую проводку. Номер выплаты уникален для партнёра.
Ошибки 409 передают стабильные `code` и человеческий `message`:

- `affiliate_payout_open_request`
- `affiliate_payout_below_minimum`
- `affiliate_payout_unavailable_balance`
- `affiliate_payout_invalid_status`
- `affiliate_payout_request_conflict`
- `affiliate_payout_duplicate_reference`

Существующий `analytics.balance` расширяется обязательными `reservedKopecks`,
`paidKopecks`, `debtKopecks`; `availableKopecks` становится доступным к новой выплате,
а `pendingKopecks`, `heldKopecks`, `reversedKopecks` сохраняют смысл. Сводки аналитики
и выплат обязаны использовать единый расчёт. Доходный ledger остаётся credit/reversal;
история выплат показывается отдельно, без смешивания выплат с выручкой графика.

## Финансовые инварианты и конкуренция

- Одна открытая заявка защищена транзакцией и partial unique index в PostgreSQL.
- Общая точка сериализации финансовых операций — строка affiliate partner.
  Существующий порядок: order -> partner -> commission/refund. Не добавлять
  блокировку order после partner, иначе возникнет инверсия и deadlock.
- Изменения договора/доступа и выплаты должны читать актуальный профиль под
  совместимой блокировкой. Снимок нельзя получить из stale read до lock.
- Резерв/списание/освобождение отражаются в неизменяемом журнале выплат; состояние
  заявки и финансовое событие меняются атомарно. Нельзя дважды вычесть paid и reserve.
- Подтверждение всегда проверяет актуальную обеспеченность и доступ партнёра.
  Одновременные refund/pay/create/reject не могут создать лишнюю выплату, потерять
  сторнирование или оставить несогласованный резерв. Ошибка не должна откатывать
  нужную автоматическую отмену заявки: проектировать возврат результата транзакции явно.
- Долг не исчезает из-за фильтра дат, паузы кода или смены договора; новая доступность
  погашает долг прежде, чем сумма становится доступной к выводу.
- Существующие guard-проверки ledger consistency и overflow сохраняются; corrupted
  ledger не даёт нулевой «успешный» баланс или разрешение на выплату.

## UI и границы работ

- Affiliate: отдельный раздел «Выплаты» в существующей навигации, карточки доступно /
  в заявке / выплачено / задолженность, актуальный минимум, ввод суммы в рублях
  с точностью до копеек, действие «Вся доступная сумма», подтверждение заявки,
  история и раскрываемые детали со снимком договора. Для ошибок — понятные короткие
  тексты, никаких технических оговорок про этапы. Долг объяснить спокойно и по делу.
- В обзоре доступный баланс согласован с выплатами; переход к выплатам. В подсказке
  статуса начисления не обещать, что уже выплаченная сумма всё ещё доступна.
- Admin: блок выплат в профиле выбранного партнёра, список/детали, формы учёта
  ручной выплаты и отказа, подтверждение и история; обновление обоих финансовых кэшей.
- shadcn/ui, RHF + zod, FSD/public API и feature-local DTO builders обязательны.
  UI не содержит прямых вызовов server actions, `_pages` только собирает страницу.
- Не менять production/DNS/банковские API. Новая миграция только в файлах и
  изолированной тестовой БД; dev/prod БД не применять. Коммит/push не выполнять.

## Проверки

API: право доступа, принадлежность, минимум (включая персональный), hold 14 дней,
самопокупка/0%, точность/overflow, snapshot договора, повтор UUID и payload conflict,
гонки create/pay/reject/refund, возврат после выплаты, погашение долга, shipping-only,
одна pending заявка в SQL, immutable events, типы/lint/build и финансовый регресс.
Frontend: загрузка/ошибка/пусто, ошибки mutation, двойное нажатие/сетевой retry,
кэш по партнёру/пагинации, формы и snapshots, архитектура, desktop/mobile QA.
Отдельный временный mock только для UI-демонстрации; это не источник доказательства
корректности серверных денег и транзакций.
