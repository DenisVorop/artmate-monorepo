# Порядок production-деплоя

`.github/workflows/deploy.yml` выполняет релизы последовательно:

1. Скачивает новые образы, пока действующий API ещё работает.
2. Поднимает PostgreSQL, затем останавливает API с таймаутом 120 секунд.
   API — единственный постоянно работающий сервис Compose, который пишет в БД
   Artmate; его фоновые обработчики останавливаются вместе с ним.
3. Выполняет миграции из нового API-образа.
4. Только после успеха запускает сервисы новой версии и проверяет их запуск.

Это сознательное короткое окно недоступности API, а не zero-downtime rollout.
Старый API нельзя оставлять работающим при несовместимых миграциях, в частности
при выделении независимых достижений.

При ошибке остановки миграции не запускаются. При ошибке миграции workflow
завершается с ошибкой, API остаётся остановленным. Автоматического запуска старого
образа или отката схемы нет: часть миграций могла уже примениться. Нужно изучить
причину, исправить её и повторить согласованный деплой совместимой версии.
Не запускать старый API на изменённой схеме для восстановления доступности.

При добавлении отдельного worker с доступом на запись в БД включить его в список
останавливаемых сервисов. Ручные внешние writers во время миграций не запускать.

Локальная проверка порядка и остановки после ошибок (без SSH и Docker):

```bash
node --test infra/test/*.test.mjs
```

Тест выполняет реальный shell-блок workflow с подменёнными командами; он не
заменяет проверку релиза на сервере и не применяет миграции к какой-либо БД.
