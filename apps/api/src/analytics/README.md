# Доставка целей заказа в Метрику

`order_created` записывается в outbox в транзакции создания нового заказа.
`order_paid` — в транзакции подтверждённого перехода в оплаченный статус.
Уникальность `(event_type, aggregate_id)` исключает повтор при checkout retry
или повторном webhook. Браузер не отправляет эти две цели; ecommerce `purchase`
остаётся отдельным браузерным событием.

## Статусы

- `pending` — ожидает отправки или повтора временно неудавшегося запроса.
- `processing` — запись захвачена worker с lease token.
- `sent` — Яндекс принял загрузку, результат ещё не подтверждён.
- `confirmed` — Яндекс вернул `PROCESSED`, исходных и валидных строк ровно по
  одной; если `linked_quantity` присутствует, оно тоже равно единице.
- `failed` — постоянная ошибка запроса, `LINKAGE_FAILURE`, несовпадение количества
  конверсий либо слишком долгая обработка файла.

`sent_at` — время приёма загрузки; `confirmed_at` — время, когда worker проверил
успешную обработку. Время самой конверсии хранится в `payload.dateTime`.
`provider_status` и `last_error` позволяют отличить приём файла от результата.

После приёма файла проверяется тот же `provider_upload_id` через GET с backoff
30 секунд — 10 минут. Повторный POST для известной загрузки запрещён. При потере
локального ответа после POST загрузка восстанавливается по детерминированному
комментарию. Отрицательный результат сопоставления не переотправляется автоматически.
Если успешно прочитанный статус остаётся промежуточным дольше 24 часов,
событие помечается ошибкой. Сетевые ошибки/408/429/5xx продолжают повторяться:
недоступность API сама по себе не доказывает потерю конверсии.

`ClientID` получается перед оформлением с ожиданием не более 800 мс. Если
счётчик или хранилище браузера недоступны, оформление не блокируется. При отсутствии
`ClientID`/`Yclid` остаётся `PurchaseId`, но он не гарантирует сопоставление:
Метрика должна знать соответствующую покупку. Без подтверждённой связи с визитом
нельзя гарантировать конверсию или подставлять идентификатор другого посетителя.

## Обновление и проверка

Перед запуском нового API применить Prisma migrations. Миграция добавляет
`confirmed`, `confirmed_at`, `provider_status` и не изменяет старые события.
Старые `sent` автоматически проходят GET-проверку по сохранённым upload ID;
исторические `order_created` не создаются. Событие без upload ID, но с `sent_at`,
не переотправляется: оно требует отдельного расследования.

Обновлять API и site согласованно: старая открытая вкладка всё ещё может содержать
прежний browser `order_created`. При проверке релиза использовать свежую вкладку.
Цели с именами `order_created` и `order_paid` должны существовать в том же счётчике;
новых event ID и переменных окружения нет.

Для сверки использовать ID заказа → outbox → upload ID → итог Яндекса,
а не только `sent`/HTTP 200. Не переотправлять историческую конверсию ради
исправления отчёта без подтверждённой атрибуции и проверки на дубликат.
