# Универсальные лайки

`LikesModule` владеет таблицами `likes` и `like_write_windows`. Идентичность объекта — пара `subjectType`/`subjectId`, пользователя — `actorId` из проверенной сессии. Полиморфных внешних ключей и enum типов в БД нет.

## API

- `PUT /likes/:subjectType/:subjectId/me` — поставить лайк; повтор сохраняет результат.
- `DELETE /likes/:subjectType/:subjectId/me` — снять свой лайк; повтор сохраняет результат.
- `POST /likes/batch` с `{ subjects: [{ subjectType, subjectId }] }` — получить до 100 состояний за запрос. Дубликаты сворачиваются, порядок первого появления сохраняется. Недоступные объекты пропускаются без раскрытия причины; неизвестный тип — 400.

Ответ состояния: `{ subjectType, subjectId, count, viewerHasLiked, canLike }`. Для гостя последние два поля — `false`. Ответы содержат `Cache-Control: private, no-store`. Все три маршрута требуют стандартный CSRF-заголовок; запись дополнительно требует авторизации. Невалидная предоставленная сессия — 401, а не молчаливый переход к гостю. Произвольный payload у PUT/DELETE запрещён.

Клиент может передать `x-artmate-like-actor` как предусловие: ожидаемый ID текущего аккаунта или `guest`. Несовпадение с проверенной сессией возвращает 409 до чтения/записи. Заголовок не авторизует запрос и не выбирает владельца лайка; он защищает запросы в полёте при смене аккаунта.

Зарегистрированы `community-work` (`subjectId = WorkshopWork.publicId`) и `blog-post` (`subjectId = BlogPost.id`). Редактор статьи не считается её автором. Реакции относятся к работе целиком, не к её редакции или месту показа.

## Подключение нового типа

1. Домен-владелец публикует versioned read-контракт в БД с полями `subject_id`, `owner_id` (nullable), `is_public`, `is_deleted`. Публикация должна содержать и временно скрытые объекты; иначе сверка сочтёт их удалёнными.
2. Владелец экспортирует определение `{ subjectType, view, denyOwnerLike }` из `contracts/`.
3. Определение регистрируется в `likeSubjectPublications` в `likes.module.ts`. Структура `likes` и алгоритмы постановки/снятия не меняются. Имена SQL-публикаций заданы только доверенной конфигурацией, не HTTP-вводом.

Нельзя выводить тип из URL, выбирать actorId по клиентским данным, вызывать бизнес-сервис владельца для повторного подтверждения сохранённого факта или изменять чужие таблицы из Likes. Контракт Users `customer_like_actors_v1` не содержит персональных данных.

## Согласованность и восстановление

Составной PK защищает уникальность; PUT использует `ON CONFLICT DO NOTHING`, DELETE затрагивает только текущего пользователя. Batch читает права и счётчики в одном Repeatable Read snapshot. Удалённые и заблокированные аккаунты не учитываются в счётчиках.

На запись действует фиксированное минутное окно: 120 разрешённых запросов на аккаунт, включая повторные PUT/DELETE. Лимит хранится в БД, действует между процессами, не ограничивает чтение или других пользователей. Окно никогда не откатывается назад при возобновлении старого запроса. Его row lock сериализует конкурентные записи одного аккаунта; изменение лайка и окна происходит одной транзакцией. Превышение возвращает 429 без изменения лайка.

`LikesCleanupJob` в CronModule каждые 10 минут вызывает восстановимую сверку. За проход удаляется до 1000 старых/осиротевших окон, до 1000 лайков удалённых/отсутствующих пользователей и до 1000 лайков удалённых/отсутствующих объектов на тип. Остаток обрабатывается следующим запуском. `SKIP LOCKED` допускает несколько экземпляров приложения. Очистка берёт блокировки в порядке запись-окно → лайки, как и команды пользователя.

Временное скрытие работы/статьи и блокировка аккаунта сохраняют лайки. Снятие с публикации сразу закрывает чтение и запись независимо от фоновой очистки. Ошибка чтения публикации откатывает сверку; недоступность БД не считается удалением объекта. Вывод типа из реестра требует отдельно решить судьбу его существующих записей.

При выделении сервиса контракт доступности переносится в принадлежащую ему read-проекцию, доставляемую из домена-владельца надёжными командами/событиями. Одна универсальная таблица сама по себе не заменяет доставку жизненного цикла и проверку полномочий.

## Проверки

`test/likes.service.spec.ts` выполняет миграцию и production SQL через PGlite; `test/likes.http.spec.ts` поднимает Nest на временном localhost-порту с настоящим service и SQL, подменяя только проверку токена. PGlite использует одно соединение: тесты пересекающихся вызовов не заменяют нагрузочную проверку нескольких PostgreSQL-сессий.

В сайте подключена карточка мозаики галереи: вариант 01 в строке автора, с областью нажатия минимум 68×44 px и сердечком 20 px. Frontend объединяет чтение карточек в batch до 100, хранит состояние по объекту и владельцу сессии. Вход продолжает намерение поставить лайк; отмена входа ничего не записывает. При смене аккаунта персональный кэш удаляется, старые ответы его не восстанавливают. Другие поверхности UI подключаются отдельно.
