# Этап 4 — недостающие контакты и владелец профиля Users

Выполнен срез в ветке `codex/email-advertising-consent`. Контактный шаг определяет и запрашивает только недостающие данные; известные корректные поля сохраняются. Профилем и его опубликованным состоянием владеет Users. Коммита и выпуска нет.

## Поведение

- Сервер оценивает значения имени и телефона, а не просто наличие User. Полный профиль пропускает контактный шаг; частичный получает известные значения и список missingFields. В UI известные поля заполнены и доступны для чтения, вводить их повторно не нужно. Те же правила действуют для уже известных контактов при регистрации на гостевой email.
- Имя остаётся одним полем, подходит одно слово. Телефон нормализуется по существующей UI-политике полного номера: 10–15 цифр, допустимые пробелы/скобки/дефисы убираются. Телефон не объявляется подтверждённым SMS, разрешение на рекламу по нему не создаётся.
- `POST /auth/flow/profile` сохраняет только временный Auth draft и ожидаемую revision профиля. Пользователь из тела запроса не выбирается; уже правильные значения берутся из Users и не переписываются клиентским вводом.
- Отмена и expiry очищают draft. Сохранение контактов не создаёт User, команду Users, credential, сессию или рекламное согласие. Регистрация/активация сначала требуют пароль с повтором; контактный endpoint не позволяет пропустить этот шаг.
- После заполнения контактов новый flow ждёт общих consent/completion gates. До реализации этапа 5 сервер возвращает `preparing`; готовые согласия и выдача сессии здесь не имитируются.

## Архитектура

`CustomerProfileValues` — публичный value contract Users для нормализации и полноты контактов. Auth использует его и read-only Users directory; не заводит свою копию правил и не вызывает Users business service.

`customer_profile_states` публикуется атомарно с изменением User. Users-owned DB trigger покрывает существующие пути изменения email/name/phone/status/authVersion, включая guest provisioning и reset. Revision увеличивается только при реальном изменении опубликованных значений. Directory дополнен profileRevision. Отсутствующая projection даёт ошибку доступности, а не ложную готовность.

`CustomerProfileCommandHandler` обрабатывает уже предусмотренный `EnsureCustomerProfileCommand`: проверяет immutable intent hash, опубликованные Auth operation/email proof и actor/authVersion, затем текущую revision профиля. User, опубликованное состояние и terminal receipt фиксируются одной локальной Users-транзакцией. Новый профиль создаётся с обычной ролью customer и исходной датой из email proof. В существующем User заполняются только недостающие/некорректные поля; прежние правильные контакты, роли, подтверждение почты и заказы сохраняются.

Несколько workers используют row claim/SKIP LOCKED; создание профиля дополнительно сериализуется по email. Внутри нет сетевых вызовов. Повтор завершённой команды не меняет receipt или профиль, бизнес-конфликт возвращает REJECTED. Инфраструктурный сбой откатывает профиль вместе с результатом, worker повторяет intent с задержкой. В новом контактном pipeline Auth не пишет User/Orders/CustomerProfileState.

Команда — доверенный внутренний intent общего completion **после применимых согласий**. Продюсер этапа 5 обязан выполнить эти gates до enqueue. Контактная форма этапа 4 команду не создаёт; в тестах команда вводится через внутренний канал для отдельной приёмки Users consumer. Сам enqueue не означает завершённый вход.

Frontend: existing RHF/zod формы расширены readonly известных полей; mapper находится в feature lib, mutation — в model, shared/actions — только HTTP transport. app/_pages, providers/host, аналитика, стили/ассеты и рабочая авторизация не переключались. Демонстрационных routes/panels/adapters нет.

## Миграция

Добавлена `20261020200000_customer_profile_pipeline`: публикация настоящих профилей существующих User, атомарное обновление read model и расширение read-only directory. Прежние миграции и Prisma-модели не переписаны; существующая таблица/команда этапа 2b переиспользованы.

Миграция не меняет User/credentials/orders, не проставляет подтверждение почты и не создаёт consent/grant. Рабочая и production-БД не мигрировались.
