## Архитектурное напоминание перед этапом

1. Сверить применимый AGENTS и фактический diff. app — route/metadata; \_pages — сборка; features — сценарии; entities — read models; shared/actions — transport. Импорты вниз/через public API.
2. RHF + zod, чистые DTO mappers/UI-state/provider в lib, mutations/server contracts в model по отдельным файлам. Provider только через HOC и обязательную структуру auth-provider. Один host, не отдельная auth-система для каждой формы/активации.
3. Не добавлять в приложение demo panel/preview route/mock-auth adapter/fixtures/debug entry. Чистые UI props/callbacks, реальное server nextStep и один completion. Макет остаётся документацией.
4. Backend — стандартные NestJS домены. Auth владеет credentials/identity/flow/session; Users — User/profile; Consents — решения/permission; Orders — заказами; Notifications — delivery. Междоменные команды/read models/results в БД с локальной транзакцией/outbox/inbox-equivalent uniqueness. Нет прямой записи чужого состояния из coordinator.
5. Password success не OTP-proof; User после заказа не готовый аккаунт; pending не ordinary session. Ни signup, ни activation, ни OAuth не выдают site session в обход общих gates. Не терять userId/заказы и не заменять существующий пароль.
6. После этапа — адресные checks, архитектурная сверка, отдельный отчёт и свежая точка продолжения. Не требовать повторно уже выбранные UI/guest решения. SSH только по отдельному разрешению AGENTS.
