# Пароль, регистрация и активация после гостевой покупки

Редакция 20.10.2026. Требования — [task.md](./task.md), этапы — [implementation.md](./implementation.md), статус — [progress.md](./progress.md). Этот документ заменяет отдельный вход по коду и запрос кода после верного пароля.

## Состояния аккаунта

| Состояние                                     | Путь                                                       |
| --------------------------------------------- | ---------------------------------------------------------- |
| Действующий credential и подтверждённый email | Обычный email + пароль, без кода                           |
| Guest User/заказы без credential              | Активация по ссылке либо подтверждённая email-регистрация  |
| Только привязанный Яндекс                     | Яндекс; локальный пароль не нужен                          |
| Новый email                                   | Регистрационный код, контакты, пароль и повтор             |
| Blocked/deleted                               | Не возрождать через signup, активацию или совпадение email |

User после заказа не означает завершённую регистрацию. Подтверждённая почта переиспользуется при входе и рекламном согласии. После верного пароля показываются только недостающие согласия; отдельного кода или ветки для старых аккаунтов нет.

## Вход по паролю

Первый экран: email, пароль, «Войти», «Забыли пароль?», «Зарегистрироваться», компактный «Я». «Войти по коду» отсутствует. Верный пароль → недостающие контакты/согласия либо completion сразу. Неверный пароль → общая ошибка и восстановление, без email-exists lookup.

Существующие hashes и срок сессии сохраняются. Свежая аутентификация отделена от прежней проверки exact email. Password login не создаёт EMAIL_CODE evidence и не отправляет OTP.

## Email-регистрация

1. Email → регистрационный код; публичный ответ не раскрывает существование аккаунта.
2. Browser-bound проверка кода с TTL/лимитами/atomic consume подтверждает exact email, без ordinary session.
3. Новый пользователь вводит ФИО, телефон, пароль и повтор. Для незавершённой гостевой записи сохраняем userId/заказы, подставляем контакты и спрашиваем только недостающее. Пароль обязателен в обоих случаях.
4. Применимые согласия → «Продолжить».
5. Общий completion ждёт результаты доменов, создаёт/активирует credential и выдаёт сессию. Не создавать дубликат гостевого User и не заменять существующий пароль.

Регистрационный код для полноценного аккаунта не становится альтернативным входом или разрешением заменить пароль: после proof предложить обычный вход/восстановление. Яндекс-only аккаунту не добавлять credential через signup в обход linking.

## Гостевая покупка и активация

Покупка без регистрации сохраняется. Checkout создаёт/использует User, привязывает заказ и отправляет служебную ссылку активации либо входа. Это не сессия и не рекламный grant. `/auth/activate-order` сохраняет назначение и применимость действующих ссылок.

1. Проверить подпись/hash, TTL, purpose, пользователя, отсутствие использования/credential/несовместимого provider account. Order ID, введённый email и payment return — не proof.
2. Браузер в фоне получает capability до расходования ссылки. Обмен ссылки атомарно создаёт browser-bound activation flow и факт exact-email verification методом ссылки. Потребление token и создание flow защищены от replay; повтор своего запроса восстанавливает тот же flow, чужой браузер не получает его. Срок не продлевается бесконечно.
3. «Завершите регистрацию»: пароль и повтор с иконками глаза. Кода нет. Контакты уже есть — пропустить; при реальной нехватке — отдельный шаг с известными значениями.
4. Общие согласия. До финального submit пароль — ограниченный draft hash, не действующий credential и не ordinary session.
5. Общий completion завершает ту же запись, сохраняет заказы и выдаёт сессию. Auth не изменяет order state или чужие доменные таблицы.

Истёкшая/повторная ссылка → понятный экран и запрос новой. Если пароль появился конкурентно, не заменять его: обычный вход/восстановление. После обмена ссылки и закрытия не обещать повторную применимость token: можно продолжить свой живой flow либо запросить новую ссылку. Ошибка позднего домена не откатывает уже подтверждённые consent facts.

Покупка на email полноценного аккаунта не заменяет его пароль/подтверждённые контакты; заказ доступен после обычного входа. Непроверенные данные заказа не перезаписывают профиль владельца.

## Восстановление

`recovery/request` возвращает общий ответ: без credential — ссылка активации, с credential — восстановления пароля. UI говорит о восстановлении доступа, не обещая смену несуществующего пароля. Purpose и проверки ссылок разделены.

Восстановление не выдаёт рекламу/согласия и не становится входом по коду. После смены пароля — обычный вход без кода; recovery endpoint не выдаёт готовую session в обход gates. Сохранить текущую политику authVersion/отзыва сессий, без незапрошенного remember-me/refresh redesign.

## Яндекс и действующая сессия

Яндекс не требует локального пароля. Проверенный результат + допустимое linking → недостающие контакты/согласия либо completion сразу. Q2 закрыт решением пользователя 21.10.2026: принимаем exact default_email из authenticated server exchange Яндекса без нового кода. Сохраняем provider provenance; настоящую прежнюю Users verification связанного адреса переиспользуем с исходной датой. Новый provider link фиксируется только в общем completion, существующий пароль/заказы сохраняются.

Действующая сессия не требует пароля/кода. Готовому пользователю — fresh callback без окна; без рекламы — шаг на новом onAuth. Пустая реклама допустима, отмена не уничтожает прежнюю сессию.

## Общая граница

Password, регистрационный proof + credential draft, activation-link proof + draft, Яндекс и сессия сходятся в одном completion. Показанные шаги нельзя обойти, готовому пользователю не добавлять кнопку.

Пароль/hash доступны только Auth, не Consents/Users/read models/requestContext/логам/callbacks. Повтор нужен UI-валидации, а не второму hash в БД. Сохраняется текущая серверная политика длины/hashing. Код/ссылки/JWT/cookies не архивируются как evidence. Подтверждение адреса и решение о рекламе — разные факты.
